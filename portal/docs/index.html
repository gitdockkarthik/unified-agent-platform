Unified Agent Platform

A production-ready monorepo for hosting, orchestrating, and chatting with specialised AI agents — each a standalone FastAPI service backed by Anthropic's Claude.

Architecture

The platform has four top-level components:

ComponentPathRole
backend//apiFastAPI service — agent registry, orchestration, chat history
portal/:3000Nginx + vanilla HTML/JS — catalogue, chat, admin, docs
agents/each on its own portStandalone FastAPI services, one per domain
shared/Python packagePydantic schemas shared by backend and agents
💡
Railway is the permanent production platform. Each component deploys as a separate Railway service inside one project. Docker Compose is for local development only.

Prerequisites

  • Docker + Docker Compose v2 — local dev stack
  • Python 3.11 — agent development (not needed for portal-only work)
  • Anthropic API key — needed by backend and each agent
  • Git

Quickstart

1
Clone and configure
Copy the env template and fill in your secrets.
bash 
git clone <repo> unified-agent-platform
cd unified-agent-platform
cp .env.example .env
# Edit .env — set ANTHROPIC_API_KEY, BACKEND_API_KEY, SECRET_KEY
2
Start the dev stack
Boots PostgreSQL and the backend. Portal is served separately.
bash 
make dev       # starts postgres + backend (hot-reload)
make migrate   # creates all DB tables (run once, or after model changes)
3
Register and publish your first agent
Use the admin form or curl.
bash 
# Register
curl -s -X POST http://localhost:8000/api/registry/agents \
  -H "Content-Type: application/json" \
  -H "X-API-Key: your-backend-api-key" \
  -d '{
    "name": "My First Agent",
    "slug": "my-first-agent",
    "description": "Answers questions helpfully.",
    "system_prompt": "You are a helpful assistant.",
    "model": "claude-sonnet-4-6"
  }' | jq .id

# Publish (paste the id from above)
curl -s -X POST http://localhost:8000/api/registry/agents/<id>/publish \
  -H "X-API-Key: your-backend-api-key" | jq .status
4
Open the portal
The agent appears in the catalogue at http://localhost:3000.
📋
The FastAPI auto-docs are at http://localhost:8000/docs and http://localhost:8000/redoc.

Portal Configuration

The portal reads two runtime values from the environment. At container startup, docker-entrypoint.sh runs envsubst to write /js/config.js?v=3 from the template. Every page then imports this file before portal.js.

Env varDefaultPurpose
BACKEND_URLhttp://localhost:8000Base URL for all API calls. In docker-compose set to http://backend:8000 automatically.
BACKEND_API_KEYemptySent as X-API-Key header on all registry and invoke requests.
⚠
The API key is visible in the browser. The admin portal is an internal tool. Do not expose it to end-users without adding a proper auth layer.

How the Catalogue Works

On load, / calls GET /api/agents — the orchestrator's public proxy that returns only agents with published status. No API key is required for this endpoint.

Agents in draft or deprecated status are invisible to end-users. They are only visible in the admin console (/admin/), which calls GET /api/registry/agents with the API key.

Agent Cards

Each card's accent colour is deterministically derived from the agent's slug using a simple hash function in portal.js:agentAccentClass(). The same slug always maps to the same colour — consistent across sessions and browsers. There are 8 colour slots: indigo, violet, cyan, emerald, amber, red, pink, teal.

The search bar on the catalogue page filters by agent name, slug, and description in real time — no server round-trip.

Sessions

A session is a UUID that groups a sequence of messages for one agent. It is created the first time a user opens /chat.html?agent=slug and persisted in sessionStorage under the key session_{agentSlug}.

sessionStorage survives page refreshes within the same browser tab but is cleared when the tab is closed. This means a user can refresh the chat page and resume their conversation; opening a second tab starts a fresh session.

Clicking New Session generates a new UUID and stores it, effectively forking the conversation. The original session and its messages remain in the database.

Streaming Responses

The chat page reads the HTTP response body via the ReadableStream API (res.body.getReader()). Currently the backend returns full JSON, so the complete response arrives in one or two network chunks. The portal then replays the text character-by-character with requestAnimationFrame, rendering at ~4 characters per frame (~240 chars/sec at 60 fps).

The architecture is ready for real server-sent events: when the backend adds a POST /api/stream/{slug} endpoint, only the response-body parsing block in portal.js:invokeAgent() needs to change.

While streaming, the assistant bubble shows a blinking cursor (.msg--assistant.streaming::after). When streaming completes, the raw text is replaced with rendered markdown.

History & Persistence

On page load the chat page calls GET /api/session/{sessionId} and renders any existing messages. This means the full conversation is restored on refresh, even after the user navigates away and returns.

When invoking the agent, the frontend sends history: [] in the request body. The backend orchestrator loads the last 40 messages from the database by session ID and passes them to Claude — the UI never needs to replay the full history.

Each message is stored in chat_messages with the session UUID, role, content, and token count.

Admin Console

Access the admin console at /admin/. It lists every agent in the registry regardless of status.

Register form

The register form at /admin/register.html auto-generates the slug from the agent name as you type. After registration you can publish immediately using the "Publish now" button that appears in the success panel.

Deployment

Local — Docker Compose

bash 
make dev        # docker compose up --build (postgres + backend)
make migrate    # alembic upgrade head
make logs       # docker compose logs -f
make test       # pytest inside the backend container

The portal is not included in the default make dev target to keep the inner dev loop fast. To run it:

bash 
docker compose up portal     # or open portal/index.html directly in a browser

Production — Railway

1
Create a Railway project and add a PostgreSQL plugin
Railway provides DATABASE_URL automatically to services that link to the plugin.
2
Add the backend service
Point it at the repo root, set Dockerfile path to backend/Dockerfile. Set env vars: ANTHROPIC_API_KEY, BACKEND_API_KEY, SECRET_KEY, CORS_ORIGINS.
3
Run migrations
In Railway's service shell or as a deploy command: alembic upgrade head
4
Add the portal service
Dockerfile: portal/Dockerfile, context: repo root. Set BACKEND_URL to the backend's Railway URL and BACKEND_API_KEY.
5
Add each agent service
One Railway service per agent, pointing at agents/<slug>/Dockerfile. Set the five AGENT_* env vars per service. Then register + publish the agent via the admin console or curl.

What Clients Receive

Each client engagement delivers a standalone agent repo — a copy of agents/agent-template/ customised for their domain. The repo contains everything needed to run the agent independently; it has no dependency on the monorepo's shared/ package.

FilePurpose
main.pyFastAPI app — /health and /invoke endpoints
agent.pyStateless AgentRunner — Claude call + tool-use loop
config.pyAll settings from env vars (pydantic-settings)
tools/base.pyToolExecutor ABC — subclass for every tool
tools/echo.pyExample tool — returns input unchanged
manifest.jsonAgent descriptor — filled in before registration
Dockerfilepython:3.11-slim; ${PORT:-8001} for Railway

The system prompt is entirely configured via the AGENT_SYSTEM_PROMPT env var. Clients can tune behaviour on Railway without rebuilding the image.

Setting Up a New Agent

bash 
# 1. Copy the template
cp -r agents/agent-template agents/my-agent
cd agents/my-agent

# 2. Configure
cp .env.example .env
# Edit .env: set ANTHROPIC_API_KEY, AGENT_ID, AGENT_SLUG, AGENT_NAME, AGENT_SYSTEM_PROMPT

# 3. Update manifest.json — fill in name, slug, description, invoke_url

# 4. Run locally
pip install -r requirements.txt
uvicorn main:app --reload --port 8001

# 5. Test
curl http://localhost:8001/health
curl -s -X POST http://localhost:8001/invoke \
  -H "Content-Type: application/json" \
  -d '{"session_id":"test-uuid","user_message":"Hello","context":{},"history":[]}'

To add a domain-specific tool, create tools/my_tool.py subclassing ToolExecutor, then register it in main.py:

python 
from tools.my_tool import MyTool
_runner = AgentRunner(tools=[MyTool()])   # add or remove tools here

Registering with the Platform

Once the agent is deployed and its /health endpoint is reachable from the backend, register it and publish it:

bash 
PLATFORM=https://your-backend.railway.app
KEY=your-backend-api-key

# Register (uses manifest.json)
AGENT_ID=$(curl -s -X POST $PLATFORM/api/registry/agents \
  -H "Content-Type: application/json" \
  -H "X-API-Key: $KEY" \
  -d @manifest.json | jq -r .id)

echo "Registered: $AGENT_ID"

# Publish
curl -s -X POST $PLATFORM/api/registry/agents/$AGENT_ID/publish \
  -H "X-API-Key: $KEY" | jq .status

The agent now appears in the catalogue and is invocable at POST /api/invoke/{slug}.

Invoke Contract

Every agent must expose exactly two HTTP endpoints:

Method + PathDescriptionAuth
GET /healthReturns {"status":"ok","agent":"<slug>"}None
POST /invokeAccepts InvokeRequest, returns InvokeResponseNone (backend handles auth)

The backend orchestrator calls the agent's /invoke endpoint when it has an invoke_url. Agents with no invoke_url are called directly by the orchestrator via the Anthropic SDK using the config stored in the registry.

}

Stateless Rule

⛔
Agents must not store state between requests. No in-memory session dictionaries, no database writes from the agent, no file system state. Every request must be fully self-contained. All context arrives through context and history.

The platform provides session persistence via the backend's chat_messages table. The orchestrator loads history from the database on every invocation and forwards it to the agent. Agents should never need their own storage.

Tool Use

Agents can expose tools to Claude using Anthropic's tool-use API. The AgentRunner in agent.py handles the multi-turn tool loop automatically — you only write the execute() method.

Creating a tool

python — tools/my_lookup.py 
from typing import Any
from tools.base import ToolExecutor

class AlertLookupTool(ToolExecutor):
    name = "alert_lookup"
    description = "Fetches alert details from PagerDuty by alert ID."
    input_schema = {
        "type": "object",
        "properties": {
            "alert_id": {
                "type": "string",
                "description": "The PagerDuty alert identifier.",
            }
        },
        "required": ["alert_id"],
    }

    async def execute(self, **kwargs: Any) -> str:
        alert_id = kwargs["alert_id"]
        # ... call PagerDuty API ...
        return f"Alert {alert_id}: CPU spike on prod-web-01, started 14:32 UTC"

Registering tools

python — main.py 
from tools.alert_lookup import AlertLookupTool
from tools.runbook_search import RunbookSearchTool

_runner = AgentRunner(tools=[AlertLookupTool(), RunbookSearchTool()])

AgentRunner.run() automatically loops until Claude returns stop_reason == "end_turn", executing each tool call and appending the result before the next Claude turn. Tool errors are caught and returned to Claude as error strings — Claude then decides how to respond.

To disable tool use entirely, pass an empty list: AgentRunner(tools=[]).

Agent Template

The canonical starting point for every new agent lives at agents/agent-template/.

text — template layout 
agents/agent-template/
├── main.py          FastAPI app — /health and /invoke
├── agent.py         AgentRunner — stateless, handles tool-use loop
├── config.py        pydantic-settings — reads all env vars
├── tools/
│   ├── base.py      ToolExecutor ABC — subclass for every tool
│   └── echo.py      Example: returns input unchanged
├── manifest.json    Descriptor — fill in before registration

├── requirements.txt 5 pinned dependencies
├── .env.example     All vars with descriptions
└── README.md        7-step guide to using the template

The template is self-contained: it imports nothing from the monorepo's shared/ package. Inline InvokeRequest and InvokeResponse Pydantic models in main.py mirror the shared schemas. This allows the agent to be extracted and delivered as a standalone repo to clients without any monorepo dependency.
